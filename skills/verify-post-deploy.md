# Verify a deployment (Stage B: post-deploy)

Report each check with the `stage,check,status,evidence` fields from [verify.md](verify.md). Stop after a failure and mark the remaining checks `NOT RUN`.

Each check below that names a command is that command; `<rows>` is the saved `scripts/site_diff.py` output from the deploy, and `site/` must still hold the build that was deployed.

`scripts/deploy.py run --execute` runs checks 1 to 4 and the restore in step 6 itself, as the last part of a [deploy](playbooks/deploy.md), and reports them in its one TOON report; its check 1 compares every built file, not only the uploads, so a stale file that the upload set missed fails too. Run the commands below by hand only to re-run one check, with the rows file that the tool saved.

1. Compare the live checksum of every uploaded file with the build: `.venv/bin/python scripts/deploy_check.py checksums <rows> --host <alias> --docroot <path>`. It reads `sha256sum` over SSH, and it fails on a missing file or a sha256 that differs from `site/`; a large pinned download in `site/` is the file its pin names, so it is compared the same way without downloading it again. A matching checksum proves only identical bytes; it does not prove the file is readable.
2. Check for stray files: `.venv/bin/python scripts/deploy_check.py paths <rows> --host <alias> --docroot <path>`. It fails on an AppleDouble `._*` file, any other dotfile (apart from `.well-known/`), or a private path in the upload set and in the live document root, which it lists over SSH, this deploy's `fm-` backup included. It only reports: a stray file already on the host is not removed by the restore in step 6, so report it for manual removal.
3. Fetch every uploaded file over HTTPS: `.venv/bin/python scripts/deploy_check.py served <rows> --base-url https://<site>/`. It fails unless each answers HTTP 200 with the bytes the build wrote to `site/`, so each changed page carries its new date, title, tags and records, and `corpus.json` (uploaded whenever public content changes) its new Corpus Record revisions. Pages and data, `corpus.json` included, are compared at any size; any other file over 20 MB, such as a large pinned download, gets a `HEAD` request whose `Content-Length` must equal its size. A 403 means the installed file is not web-readable.
4. Load each changed page once in a headless browser: `.venv/bin/python scripts/deploy_check.py console <rows> --base-url https://<site>/`. It fails on any console error, naming the URL of each resource that failed to load. It opens the site root first, in its own browser session, so a deck as the first changed page needs no manual warm-up.
5. Judgment: that the build holds what the request asked for (the expected date, title, tag or record on each changed page) was settled when Stage A reviewed `scripts/site_diff.py`; step 3 proves the live bytes are that build. Report the pages and records the request named.
6. If any check fails, restore the preserved prior files according to [Atomic safe deploy](principles/atomic-safe-deploy.md). Report the mismatch and the restore result.
